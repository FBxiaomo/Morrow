## 1. 产品概述

### 1.1 背景与问题

计时工具早已过剩，但「安心开始一段时间」仍然稀缺：专业番茄应用把人按在 Gantt 式的任务管理里，桌钟应用要么是纯装饰、要么把屏幕塞满提醒。用户真正需要的是一个**打开即沉浸、离开不焦虑**的空间——时间可见，氛围随真实天气呼吸，专注只需要一次空格。

### 1.2 一句话定位

**为学习、办公与休息提供低干扰的天气氛围时钟。**

价值主张：

- **打开即全屏**——不是挂在桌面上的小组件，而是应用本身就是桌面（v1 立项决策）；
- **四个空间，不是四张皮肤**——天幕 / 数字工作室 / 窗边 / 静谧编辑各自独立配置，切换主题即切换一个世界；
- **天气是氛围，不是信息面板**——真实天气驱动光线、雨雪与玻璃，失败时诚实说「正在显示上次天气」；
- **专注是一个闭环**——任务意图 → 计时 → 到时反馈 → 本地记录，长时间离开不虚构、不惩罚；
- **本机优先**——无账户、无支付、无云同步、无遥测；设置可导出，数据可清空。

### 1.3 名称与品牌

中文名「末时钟」，英文名 **Morrow**（2026-11-22 起统一，前称 Horloge）。Morrow =「次日、明天」，与「给下一段时间的自己」的产品语气一致。品牌注意事项（来自 2026-11-13 审查）：

- 「末」是否被理解为末日/结束，与安静陪伴定位是否匹配，需向目标用户测试后再定对外主叙事；
- 首屏与介绍页统一使用「末时钟 · 天气氛围与专注时钟」降低理解成本；
- 携带旧名 `horloge` 的存储键与导出标识迁移已立项（`specs/changes/2026-11-22-morrow-identity-migration/`，B 阶段待实施）。

## 2. 目标用户与使用场景

三类首批用户（**均为假设，需访谈验证**——审查文档建议招募 10–20 位符合场景的试用者）：

| 画像 | 场景 | 关键诉求 |
| --- | --- | --- |
| 学生 | 副屏/第二块屏幕常驻；晚自习 25 分钟专注 | 开始仪式感、到时提醒、不被打扰 |
| 居家办公者 | 桌边平板；用「数字工作室」做办公主场景 | 大数字可读、当前任务一目了然、常亮 |
| 桌面美化爱好者 | 自选背景图片 + 字体 + 配色，四主题各配一套 | 个性化深度、真实预览、数据可带走 |

核心使用闭环（产品主叙事，所有功能围绕它收敛）：

```
打开自己的空间 → 开始一段专注 → 收到结束反馈 → 下次继续使用
```

优先形态：**电脑副屏与桌边平板的浏览器全屏 / PWA**。窄屏手机横竖屏是兼容目标而非第一形态（844×390 横屏已按「先移除装饰再紧凑」原则适配，有测试断言）。

## 3. 产品目标与成功指标

| 层级 | 指标 | 说明 |
| --- | --- | --- |
| 北极星 | 「首次成功完成一次专注」的转化率 | 新用户打开后，无帮助指引即可完成：选时长 → 计时 → 到时反馈 |
| 习惯 | 七日回访率、专注完成率 | 判断「第二次打开能找回配置」是否成立 |
| 质量 | 会话 pageerror 率、弱网/离线可用性 | 全部异常路径有诚实降级，不出现「看似在工作」 |
| 辅助 | 常驻时长 | 仅作辅助指标，**不得**把空置页面当作用户价值（审查明确警示） |

当前约束：产品**无遥测**（本机优先原则），以上指标需通过小规模试用观察与人工访谈采集，不做埋点先行。

## 4. 功能需求（按能力域）

优先级：P0 = 对外发布前必须；P1 = 下一轮完善优先；P2 = 有试用数据后再定。**每域的行为细节以 `specs/capabilities/<域>/spec.md` 的 EARS 编号为唯一真相**，本节只保留产品层摘要。

### 4.1 时间与信息呈现（time-display）· P0

12/24 制式、秒的四种形态（数字/进度条/组合/无）、日期、农历与节气、月相、世界时钟（≤5 城、三级解析、无效条目给原因不显示 `--:--`）。时钟在任何视口与主题下不与任何组件重叠（有测试断言）。

### 4.2 四主题与个性化（themes-personalization）· P0

四主题独立 profile（外观/背景/内容键全局共享天气城市与专注时长）；恢复默认搭配；背景四类（摄影/渐变/纯色/自选图片，图片浏览器内压缩入 IndexedDB）；8 组字体栈 + 本机字体选择；设置面板五分页、不透明底色。

### 4.3 天气（weather）· P0

真实/自选双来源；城市搜索（中文、候选、消歧）与定位（仅点击后请求，**定位后反解中文地名**再接通实况——2026-11-23 新增，含失败诚实占位与晚到结果竞态守卫）；缓存 30 分钟；断网显示上次天气并明示；自选天气七分类 × 四时段。**商用前必须网关化（见 §9 风险）**。

### 4.4 氛围渲染（atmosphere-rendering）· P0（渲染）+ P2（实验）

单主循环预算制（33/16/66ms、DPR ≤ 1.5、隐藏停画、reduced-motion 冻结）；写实粒子与数字打湿互动（非窗边主题）；工作室天气转室内光；体积云（写实条件触发）；窗边 WebGL 玻璃雨 + Canvas 回退链。麦克风律动为**实验功能**，不在产品主线承诺内。

### 4.5 专注计时（focus-timer）· P0

任务意图（≤80 字）→ 15/25/45 快捷时长 → 时间戳驱动计时（后台/休眠/跨刷新不丢精度）→ work/short/long 阶段机 → 长时间离开暂停等待确认（不虚构补算）→ 完成回顾 + 可选系统通知 → 本地历史（≤100 条）与今日统计。双空格不误结束。

### 4.6 设置与数据（settings-storage）· P0

schema 驱动 37 键设置；损坏数据安全回退；**持久化失败诚实反馈**（「仅本次有效」+ 重试）；版本化配置导出/导入（≤1MB 校验）；清空本机数据（二次确认）。

### 4.7 离线与常亮（offline-pwa）· P0

生产注册 Service Worker：核心界面可离线重新打开；跨源请求不拦截（天气依赖网络，离线明示）；屏幕常亮经 Wake Lock，不支持则诚实关闭并提示。

### 4.8 交互层（interaction-shell）· P0

快捷键契约（`1–4/S/Esc/F/H/T/空格/M`，全守卫）；工具条闲置 3600ms 淡出、触屏不隐藏；纯净显示（`H`，只留时间与用户选择的信息，必有清晰退出）。

## 5. 非功能需求（NFR）

| 域 | 要求 |
| --- | --- |
| 性能预算 | 帧预算 33/16/66ms（默认/写实/轻量）；DPR ≤ 1.5；WebGL 帧缓冲 ≤ 1.8M px；写实粒子上限（700/180/100/240/48）；隐藏即停画。数字出处见 `specs/capabilities/atmosphere-rendering/spec.md` |
| 可读性 | 界面文字 ≥ 11px（测试强制）；触控 ≥ 40px；对比度目标 WCAG AA；`prefers-reduced-motion` 全局短路 |
| 可靠性 | 一切降级链显式可测：WebGL→Canvas、存储失败→诚实提示、断网→上次天气、损坏数据→默认值。**不允许任何「看似在工作」状态** |
| 隐私 | 全部数据本机（localStorage/IndexedDB）；麦克风音频只在本机处理；定位仅在用户点击后请求；导出诊断前让用户查看内容 |
| 质量门槛 | `npm run build`（tsc strict）+ 46 项 Playwright 回归全绿才算完成；Open-Meteo 域名在测试中永不真联网 |
| 体积基线（0.2.1 审查记录） | JS ≈ 101.6 kB（gzip 35.8 kB）；CSS 33.4 kB；三张 WebP 共 ≈ 619 kB；内置字体 ≈ 1.15 MB（按需加载，不默认进首屏请求） |

## 6. 边界与非目标

- **不做**：支付、账户体系、云同步、多语言 i18n 框架、破坏沉浸的广告位。
- **暂不进主线**（审查结论）：AI 助手、社区、排行榜、复杂任务管理；第五/第六主题（先把四主题各自做出不可替代的使用理由）。
- **定位红线**：不做 Tauri 窗口挂载（浏览器全屏即桌面）；粒子描字不回主线（v3 决策，已摘除）。
- **不确定项不承诺**：没有能耗实测前不宣称「低功耗」；没有跨浏览器实测前不宣称「全平台」。

## 9. 商业化方向（假设，未验证）

沿用审查结论的两步走：

1. **免费核心**：基础时钟、基础主题、可靠计时、离线能力、数据导出——用小规模试用确认复用场景。
2. **付费理由验证**：精选场景包、完整声音包、多套搭配与高级自动切换，**优先测试买断/主题包**；只有出现持续云服务时再验证订阅。

支付前必须具备（当前均未建设，列入阶段 D 前置条件）：明确权益、购买确认、订单查询、权益恢复、退款/客服路径、回调幂等；权益判断与支付回调须在可信后端，**不得依赖 localStorage 标记**。

服务成本模型：天气调用量 ≈ 活跃用户 × 前台小时 × 每小时刷新次数（30 分钟 TTL）+ 主动刷新与搜索，不能按注册数估算；缓存、限流与预算监控归服务端。

## 11. 需求追踪约定

- 本 PRD 的功能需求 = `specs/capabilities/<域>/spec.md` 的 FR/NFR 编号集合；行为改动**必须**先修订规格（AGENTS.md R1），并在提交说明中列出受影响编号。
- 新增产品级方向（新用户群、新商业模式、新平台）先改本文件；能力级行为走 `specs/changes/` 提案流程。
- 本 PRD 与规格、规范的三方链接：README「文档体系」、`AGENTS.md` §7 文档地图。
